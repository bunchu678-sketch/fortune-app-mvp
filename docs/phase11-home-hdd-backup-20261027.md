## B. 構成と保存内容

```text
新規合成SQLite → SQLite Backup API → 整合性/FK/schema確認
 → gzip(level 6) → 既存AES-256-GCM → 模擬VPSステージ
 → 模擬pull → .partへ受信・再開 → AEAD・SHA・SQLite検証
 → 模擬HDDへrename → 永続成功記録 → 受領ACK → 30日整理
```

VPS/PC/HDD/独立台帳の役割を、毎回新しく作る専用TemporaryDirectory内の別ディレクトリで模擬する。
物理的に別機器の試験ではない。任意のDBパス・SSH先・HDD先を受け取るインターフェースはない。
既存の利用者DB・実個人情報・実VPS・実HDDには接続していない。
暗号文の同一性をSHA-256で、改変の検出をAES-GCM認証タグとメタデータAADで確認する。
復号後のSQLiteはメモリ上で検証する。受信先には平文DBを作らない。

直近容量調査は、正式計算1,000件で整合DB 38,772,736 bytes、gzip 8,092,094 bytes、
gzip 30世代 242,762,820 bytes。完成Excel/PDFはDBに恒久保存されない。
出典は開発元 `docs/backup-capacity-20261027_notes.md` と対応するresults.json。
今回の障害試験は小さな合成DBを使い、鑑定サイズの再測定とは呼ばない。
今回のJSON暗号封筒はbase64を含むため、実装のまま1,000件に適用すると
約10.79MB/回、約324MB/30世代にメタデータが加わる**試算**となる。
暗号化後の正式1,000件を再実測した値ではない。初期確保5GB案で十分な余裕がある。
試験上限は平文64MiB、封筒96MiB。将来増加時は上限と処理時間の再検証が必要。

## C. Windows側の日次処理

- JSTの具体時刻は必須引数。03:00は試験fixtureだけで、本番設定ではない。
- `runs`、`backups`、`events`、`outbox`、`metadata` を専用制御DBに永続化。
- OSのファイルロックで別プロセスを排他。プロセス終了で解放され、古いPIDを信じて解除しない。
- 同日の正常完了済みジョブは再保存しない。受信途中は接頭部を照合して続きから取得。
- rename後・成功記録前、成功記録後・ACK前も再検証して再開する。
- 取得再試行は1呼出し最大3回。ジョブ全体の再試行はスケジューラ案で10分間隔3回。
- 日付の巻き戻りは拒否。停止中の過去日のバックアップを捏造せず、現存世代だけ回収。
- 既に認証確認済みの過去世代は、永続受領記録に結び付く同じSHA/サイズ/メタデータを確認。
  最新正常世代は削除前に再度復号検証する。

`research/home_backup_task_draft.py` はXMLを標準出力に生成するだけ。
StartWhenAvailable、WakeToRun、IgnoreNew、起動2分後トリガー、30分実行上限を含めた。
時刻は `+09:00` を明示し、配備時にWindowsのタイムゾーンも確認する。
電源断からの起動をWakeToRunだけで保証できない。停電・再起動・スリープは別々に確認する。

XMLは未登録で、実行先も**毎回新しい合成デモ**、実行アカウントも未確定の仮値。
このデモを定期実行しても実バックアップ運用にはならない。
本番アダプター、実行ID、資格情報、アクセス権、ログオン不要の実行条件は後工程。
新しい常駐サービスは追加していない。

## D. 30日保持と例外

期限はVPSで確定した作成日時+30日。Windowsのコピー日時・mtimeでは延長しない。
日次に受信・検証・記録した後で、管理台帳に載る自分の `.enc` / `.part` だけ削除する。
削除開始前に `delete_pending` を永続化し、削除直後に異常終了しても次回完了できる。
未知のファイルや領域の不一致では削除を止め、注意状態にする。
監査・独立最新台帳には別の保持根拠があるため、この30日整理に混ぜない。

PC停止中は処理できない。再接続後、取得可能な世代を回収してから整理する。
最後の正常世代が期限超過でも、新しい正常世代がなければ保持し、
`retention_overdue` として注意・通知待ちを記録する。
正常性そのものを確認できない場合も `retention_unverified` で削除を止める。
これは正常な30日削除完了ではない。自動的な無期限保存の承認でもなく、
未解決警告を運用担当者が確認して復旧・削除判断する必要がある。

**過去の「30日後削除」との相違**：今回の最新本人希望は日次整理と停止後の後追いを認める案。
期限どおりの物理消去を常時保証する方式ではない。
合成環境での採用候補に限定し、利用規約・対外説明・個人情報保持条件の整合性は本番前の本人判断。
鑑定履歴削除、解約後の復旧猶予、User削除等の既存仕様は変更していない。

## E. VPSステージの具体案

本番案は専用非公開領域、暗号文3日、上限256MiBを出発点とする。未承認の候補値。
今回のテストでは上限を2MiB等に縮め、容量不足を注入した。
通常の順番は期限整理→新規作成→受領確認。生成と整理は同じVPS側OSロックを使う。
1,000件の暗号封筒3回分は約32.4MBという試算で、256MiBには余裕がある。
圧縮前整合コピー約38.8MB、圧縮・暗号化処理、DB/WALの成長も別に空き確認する。

受領済みはPCの耐久的成功記録後のID+SHA ACKで判定。
未受領でも3日超の古い世代は整理候補となるため、長期停止後に全日分を回収できる保証はない。
最後に検証できるステージ世代を保護し、超過を記録。
全世代を検証できないときは削除しない。容量上限時は新規作成を失敗扱いにし、
正常世代を容量確保のために消さない。試験の容量上限は合成注入で、実VPSの空き監視ではない。

削除後も個人情報を含まない世代メタデータを残し、PCが `staging_gap` を検出。
作成日が抜けた場合は `generation_gap`、最後の作成/取得が1日超なら
`generation_stale` / `offsite_backup_stale`、未受領1日以上ならVPS側で `delivery_overdue`。
VPSステージは外部バックアップではなく、VPSごと失われ得る。

## F. 暗号と鍵回復

| 方式 | 利点 | 条件・課題 | 今回 |
|---|---|---|---|
| AES-256-GCM共通鍵 | 既存標準実装を再利用でき、PCで完全な検証ができる | VPSとPC双方が復号可能。鍵をHDD暗号文と分離し、OSアクセス権・鍵保管庫・鍵ID/更新手順が必要 | 合成鍵のみ実装・検証 |
| 公開鍵による封筒暗号 | VPSは公開鍵だけを持ち、自宅秘密鍵を置かずに暗号化できる | 確立した実装の選定、署名/送信者認証、Windows回復、依存追加の判断が必要。公開鍵への暗号化だけで送信者は証明できない | 比較のみ、未実装 |

本番候補はまず既存AES-GCMを活かす案。実鍵はGit/Notion/引数/ログに保存せず、
PC故障時の回復用コピーを別媒体に保管し、担当者・保管場所・回復試験を決める。
鍵を失うとHDDがあっても復号できない。HDDと同時に失われる保管方法を避ける。
合成試験は別roleのファイルに使い捨て鍵を置くだけで、本番用の安全な鍵保管実装ではない。
鍵欠落・別鍵・オフライン合成鍵からの回復を検証した。本番鍵の作成/配置は行っていない。

平文の整合コピーは合成領域内に限定し、通常/例外処理で削除する。
生成中にOSごと停止した場合の残骸は次の生成開始時に所有名を確認して整理する設計。
ファイル削除は媒体上の完全消去を意味しない。本番では専用アクセス権、暗号化ボリューム、
一時領域の保管条件を決定する。生成元の合成DBと鍵もデモ/試験終了時に専用領域ごと片付く。

## G. 独立最新台帳と復元制約

revision、watermark、前revisionのハッシュ連鎖、内容SHAをAES-GCM認証付きで模擬VPSから模擬PCへ保全する。
`note_change` で未公開変更を先に記録し、完全公開後に確認点を進める。
欠番、改変、古い確認点、未公開、PC側台帳消失、同期/復元中の新規変更は拒否。
既存の正式な復元適用処理を使い、削除済み鑑定の再出現を防ぐ。
B2Cと別Organizationを保護し、全ユーザー停止・全セッション失効・reset token無効化を確認。
復元先は `:memory:` のみ。実DBへの書込み・利用再開・アカウント再有効化機能はない。

`truth/` は「独立の場所から最新性を証明できる」場合を模擬する**試験用の正解情報**。
同じPCの別フォルダを本番の独立機関と扱っていない。
実アプリの変更イベント連動、認証済み配送、独立した最新revision証明の本番接続は未実装。

後工程のイベント対応は、履歴/人物/User削除と契約の終了/再開/世代変更を列挙し、
アプリの確定処理と送信待ち記録の取りこぼしがないように結び付ける設計とする。
合成試験では既存Repositoryで変更→`note_change`→正式manifest export→`publish`→`sync`を明示実行。
台帳の生成/公開もVPS側OSロックで直列化する。実アプリへの自動フックではない。
PC側は受信ファイルを耐久化してからrevisionを進めるので、ファイル保存直後の停止にも再実行できる。

**未解決の重要条件**：PC通信断中にもVPS上で削除・契約変更を続け、そのVPSを失うと、
自宅の古い台帳だけでは「後続変更なし」を証明できない。
ハッシュ一致や更新時刻の新しさだけで解除しない。証明できなければ復元後の利用再開は禁止。
無課金でこの穴を閉じる候補は、対象変更の受付を独立側ACKと連動させ、
PCへ確認できない間は対象変更を確定させない設計。ただし可用性が下がり、
アプリ本体・業務操作に及ぶため今回実装しない。本人の判断と別作業範囲が必要。
