## B. 4世代の処理

```text
新規合成SQLite → 既存SQLite Backup API → 整合性/FK/schema確認
 → gzip → 既存AES-256-GCM → 模擬VPSステージ
 → 模擬pull/.part再開 → SHA/AEAD/SQLite検証 → 模擬HDDへrename
 → 耐久的成功記録 → ID+SHA受領ACK → 30日整理
```

`BackupSchedule`に生成時刻一覧、取得遅延、生成許容遅延、警告猶予を明示する。
`slot(now,schedule)`はJST予定日時（例 `2026-10-27T12:00+09:00`）を返す。
制御SQLiteの既存TEXT列をそのまま利用し、アプリDB schemaは変えない。
元の `created_at` は実際にコピーを開始した合成時刻であり、予定時刻へ書き換えない。
同じ枠は同じID/暗号文を返し、別枠は新しいSQLite整合コピーを作る。
ID・作成日時・枠・平文SHA・schema情報は暗号認証に結び付ける。

新規生成は予定から30分以内という試験/候補条件。枠を逃したら過去のDBを再現した扱いにせず、欠落を記録する。
既に作成済みの同枠コピーは30分後でも再利用でき、公開直後に停止したコピーは真正性確認後に記録を完了する。
未作成の過去枠は生成しない。予定枠と実作成時刻を区別する。
PC再起動後は残っている未取得の全世代を回収し、存在しない過去世代は補わない。

`run_slot()`が時間枠単位の実行。`run_daily()`は既存試験用の互換名で、同じ時間枠処理を呼ぶ。
既存の単一時刻fixtureも回帰確認するが、実運用案は4回方式。
制御DB/ファイルは新規合成領域専用で、旧実運用状態の移行機能ではない。
将来時刻を変更するときは、既存の枠ID・保管世代との対応をレビューして切替し、既存履歴を上書きしない。

## D. 保存容量とステージ評価

MB/GBは10進、MiB/GiBは2進。正式1,000件の既測定値はSQLite 38,772,736 bytes、gzip 8,092,094 bytes。
今回は正式1,000件の容量を再測定していない。障害/保持試験は小さい合成DBを使用する。
現行暗号封筒のモデルはAES-GCMの28 bytesとbase64拡張、ヘッダー等4KiBの予算を加え、
`4*ceil((8,092,094+28)/3)+4,096 = 10,793,592 bytes/回` とした。
これはヘッダー予算付きの試算で、暗号化後の正式1,000件の実測ではない。

| 対象 | 試算 |
|---|---:|
| HDD 4回×30日＝120世代 | 1,295,231,040 bytes（約1.30GB / 1.21GiB） |
| VPS 3日＝12世代 | 129,523,104 bytes（約129.5MB / 123.5MiB） |
| VPS 12世代＋次の1世代 | 140,316,696 bytes（約140.3MB / 133.8MiB） |
| 同13世代が単純に2倍成長 | 280,633,392 bytes（約267.6MiB） |
| 従来ステージ上限 | 256MiB＝268,435,456 bytes |
| 拡張候補 | 512MiB＝536,870,912 bytes |

現規模の12+1世代モデルは256MiBに収まる。一方、2倍成長モデルは超えるため、
本番空き容量を確認して512MiBへの拡張を推奨候補とする。本番値は未確定。
ステージ上限は暗号文領域の制限であり、元DB/WAL・平文整合コピー・制御記録等の総上限ではない。
現規模でも平文コピー約38.8MBが別途必要。生成・検証用の作業空きは1GiB程度を候補とし、
実DB/WAL成長・メモリ・実測ピークを含めて次工程で調整する。これは実測したピーク値ではない。

HDD側は2倍成長・124世代分の作業枠・管理10%・空き20%を見たモデルで約3.68GB。
初期確保5GBの目安を維持できる。約700GBの空きは本人申告であり、今回は実HDDを確認していない。
容量削減のために世代を危険にさらさず、計測に応じて領域拡張を優先する。

成功結果には暗号文容量、部分受信容量、ステージ容量、前回からの保存容量差を返し、前回容量を制御DBに保存。
空きは合成領域のあるホストディスクだけを測る。実HDD容量の測定実装/検証とは呼ばない。
256MiB等のステージ論理上限と、注入した空き不足も合成試験する。
本番アダプターでは承認済みのHDD識別が一致した保存先だけで容量を計測し、別ドライブへ退避しない。

## E. 30日整理とPC停止

保持は元の実作成日時+30日。単に最新120個を残す方式ではない。
各取得成功後に整理するので、通常は1日4回、少なくとも日次の整理となる。
正常継続時は約120世代。遅延/作成時刻のばらつきで一時的に個数は変わる。
コピー日時/mtimeで期限を延ばさず、管理対象 `.enc` / `.part` だけを消す。
未知ファイル・別媒体・検証できない状態では削除を止める。削除前の `delete_pending` 記録と再開を維持。

PC停止中は取得/整理不能。復旧後に残存世代を回収してから整理する。
最後の正常世代は新しい正常世代がなければ保護し、期限超過を `retention_overdue`、
正常性を証明できなければ `retention_unverified` として注意/通知待ちにする。
これは正常な30日消去完了でも無期限保存の承認でもない。担当者の確認・是正が必要。
過去の厳密な30日後削除と、停止後の後追い整理との差は、本番の利用規約/対外説明で確認する。
既存の履歴削除、解約後復旧猶予、User削除は変更しない。台帳/監査は別の保持根拠で扱う。

VPSステージは3日を維持。期限整理→新規生成が基本で、3日超の未受領世代も整理され得る。
PC停止が3日を超えると全世代を回収できない可能性がある。失われた枠を生成し直さず通知待ちにする。
最後に検証できるステージ世代は保護する。上限時は新規作成を失敗にし、正常世代を容量確保のために消さない。
VPS上のコピーはVPSごと失われ得るため、外部バックアップの代わりではない。

## F. Windows自動運用

XML生成は4つのCalendarTriggerと起動2分後のBootTriggerを出力する。
JSTの `+09:00`、StartWhenAvailable、WakeToRun、IgnoreNew、10分間隔3回再試行、30分実行上限を維持。
OSロックも併用し、タスク設定だけに排他を任せない。部分受信は照合後に再開し、
rename後・成功記録後・削除直後の停止も永続状態から再実行する。
StartWhenAvailableの補完は即時実行保証ではなく、停止中の各回を別々に再現する機能でもない。
PC起動後の1回の処理で現在取得できる未取得世代を列挙して回収する。
電源断からの起動、スリープ復帰、未ログオン実行、HDD復帰は実機で別々に確認する。

XMLは未登録で、実行アカウントはレビュー用仮値。実行先は毎回新しい合成デモ。
このXMLをそのまま登録しても本番バックアップ運用にはならない。
実際のSSH取得/恒久制御領域/実HDD識別/Windows資格情報/送達通知への接続は次工程。
通知待ちoutboxは実通知ではない。PC停止中は自分で送信できず、VPS側未達通知も必要。
双方停止中は通知できないため、担当者の確認方法も決める。

## G. 暗号・台帳・復元の安全条件

既存Node標準AES-256-GCMを変更せず使用。ランダムnonce、認証タグ、AAD、SHAを検査。
平文コピーは専用合成領域に限定し、通常/例外終了で削除。硬い停止の残骸は次の生成時に所有範囲だけ清掃する。
復号/SQLite整合検査/復元はメモリだけ。実DB上書き・本番用削除executor・自動再開を追加しない。
合成鍵は使い捨てで、本番用秘密鍵は生成/配置しない。鍵のHDD暗号文との分離、
PC故障時の別媒体回復、所有者/代理、OS権限/保管方法は本番設定時に確認する。

**15分ごとの独立最新台帳同期は本人指示により保留。**
変更ごとの外部ACK必須化、新台帳サービス、契約/削除処理の大規模変更も実装しない。
この保留を理由に通常バックアップの改修や導入準備を延期しない。
既存台帳検証コードと試験用の独立正解情報は維持し、欠落/古いrevision/改変/不完全/復元中変更は拒否する。
別フォルダを本番の独立証明元と呼ばない。4回の全量コピーだけでは、以後の削除・契約変更の最新性を証明できない。

復元後は全ユーザー停止、セッション/reset無効化、削除情報の再適用、契約世代照合を維持。
B2C/別Organizationを保護する。最新の削除・契約情報を証明できなければ利用再開禁止。
本番事故時に最新性を確認できない状態が起こることは残る制約として明示する。
本番バックアップ取得を始める工程と、復元後の利用再開を承認する工程を区別する。

XMLのactionも合成デモであり、実環境アダプター/資格情報/保存先へ接続する設定はまだない。
